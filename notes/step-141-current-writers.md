# Step 141 — Files from current writers: one false `Invalid`, one sentence refuted

*2026-09-25. Measurement only: no specification, test or code changed,
except one line of `docs/comparison.md` that this measurement refuted.*

## Why

Step 140 counted the open gaps in test files written by implementers, and
said the stronger measurement would be files from the writers people use
today. This is that measurement. The question is the same as always: does
this verifier say what `c2patool` says on a real file, and if not, is the
difference a known and chosen one?

### 1. Microsoft Bing Image Creator, 9 files: a false `Invalid` here

| this verifier | 0.27.22 | 0.28.0 |
|---|---|---|
| `Invalid`, `general.error` | `Valid` | `Invalid`, `signingCredential.invalid` (*"certificate missing required EKU"*) |

This verifier's explanation is *"piece out of order at offset 2: packet
sequence number expected 1, found 0"*. Every one of the nine files holds
its whole manifest store in a single APP11 segment, and that segment's
packet sequence number Z is **0**:

```
APP11 @2 len=13091 CI=4a50 En=59136 Z=0 LBox=13081 TBox=jumb
```

SPEC-001 AC3 requires the first piece to carry Z = 1, and so refuses the
file before a single box is read. `c2pa-rs` does not look at the first
piece's Z at all. Its reader (`sdk/src/asset_handlers/jpeg_io.rs`,
`read_c2pa`, at `ada3e4a`) recognises the first piece by the C2PA
superbox type at bytes 24–28. For later pieces with the same `En`, it only
checks that Z has grown. 0.28.0's `Invalid` is not about the container:
it reads the store and objects to the Microsoft signer's EKU, as in
group 2.

This is the only difference where this verifier alone refuses a file from
a mass-market writer. It fails closed, so it is not a wrong `Valid`, but
it is a wrong `Invalid` on every Bing image measured.

**Not yet settled:** what ISO/IEC 19566-5 and the JPEG XT box format say
the first Z must be. That is read before anything is written.

### 2. OpenAI signers issued by Trufo, 6 files: 0.28.0 differs, not this verifier

| this verifier | 0.27.22 | 0.28.0 |
|---|---|---|
| `Valid` | `Valid` | `Invalid`, `signingCredential.invalid` (*"certificate missing required EKU"*) |

OpenAI signs with two different leaf certificates, both with the subject
`CN=OpenAI Media Service`. The two tools only disagree on the second:

| issuer | EKUs of the leaf (`openssl x509 -ext extendedKeyUsage`) | files |
|---|---|---|
| `SSL.com C2PA ICA R1 2025` | E-mail Protection, `1.3.6.1.5.5.7.3.36`, `1.3.6.1.4.1.62558.2.1` | agree |
| `Trufo C2PA Claim Signing CA (2025)` | `1.3.6.1.4.1.62558.2.1`, `1.3.6.1.5.5.7.3.36` | differ |

This is step 112's divergence: a leaf whose EKUs are the C2PA
claim-signing OID and documentSigning, without emailProtection. Step 112
chose C2PA 2.4 §14.4.1 over 0.28.0 and nothing here changes that. But
`docs/comparison.md` said *"Every real signer measured also carries
emailProtection, so the difference shows on synthetic files only"*. **That
is refuted.** It shows on OpenAI images published this month. The line
now says so.

### 3. Adobe Firefly, 7 files: a documented divergence

| this verifier | 0.27.22 | 0.28.0 |
|---|---|---|
| `Invalid`, `signingCredential.expired` | `Valid` | `Valid` |

The signer has expired at now. The file's timestamp would place the
signature inside the signer's validity, but this verifier trusts a
timestamp authority only through configured anchors (ADR-0004,
`docs/comparison.md`, *"Where this verifier differs by design"*). The
Truepic, Amazon and Pixel files already show the same divergence.

## Reasoned

- **No wrong `Valid` was found on any file from a current writer.** Where
  this verifier says `Valid`, both `c2patool` versions say `Valid` too,
  except for the six Trufo files, where the divergence is 0.28.0's and was
  chosen knowingly.
- **The Bing refusal is worth a spec** once the norm has been read. A
  CMS will meet Bing and Microsoft Designer images, and this verifier
  refuses them for a detail of the container. The fix is narrow (the first
  piece's Z). A later piece out of order stays refused, as AC3 says.
- The open conformance issues (#1, #5–#9, #12) did not show up in any of
  these 78 files, which supports step 140's conclusion.
