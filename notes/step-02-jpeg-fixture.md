# Step 02 — The signed JPEG fixture, and what a JPEG looks like inside

*2026-09-19.* Before SPEC-001 can say "extract the manifest store from a
JPEG", there has to be a JPEG with a manifest store in it, made in a way
anyone can repeat, and a measurement of what is actually in it. This step is
that fixture and that measurement. No verifier code.

## The fixture

`tests/Fixtures/fixture-signed.jpg` (96,939 bytes, SHA-256
`b004c197b6bf32c3bf816e46667ffc8513b68a06e8dabb3bc5ab8ba9ca865082`) was made
from `tests/Fixtures/fixture-unsigned.jpg` (2,128 bytes, SHA-256
`7753f456cc7269c6982e95218534a07f629eea727cc82ac75cedd41d2d95c679`; a 64×64
test pattern generated by ffmpeg, taken from the sister library's fixtures)
with:

```
c2patool fixture-unsigned.jpg -m fixture-signed.manifest.json -o fixture-signed.jpg
```

`c2patool 0.27.22`, the c2pa-rs ES256 **test** certificate chain
(`es256_certs.pem`, byte-identical to `contentauth/c2patool` `sample/`). The
manifest definition is `tests/Fixtures/fixture-signed.manifest.json` with the
key and certificate paths replaced by placeholders; the private key is not in
this repository and never will be. The one action says
`digitalSourceType: algorithmicMedia` — "created purely by an algorithm" —
because that is what an ffmpeg test pattern is; the fixture claims nothing
about itself that is untrue.

## What a JPEG is, for the reader who has never looked inside one

A JPEG is a sequence of *segments*. Each starts with a two-byte *marker*
(`FF` followed by a code) and, for most, a two-byte length. A reader hops
from marker to marker. A few markers matter here: `FFD8` SOI (start of
image), `FFDA` SOS (start of scan — the pixel data follows, up to `FFD9`
EOI), and the *application* markers `APP0`–`APP15` (`FFE0`–`FFEF`), which
the JPEG standard set aside for data that is not pixels. Cameras put EXIF in
APP1. A reader that does not know an APPn segment skips it; that is why
anyone can add one without breaking the picture.

C2PA uses **APP11** (`FFEB`). A segment's length field is two bytes, so a
segment holds at most 65,535 bytes; a manifest store is often larger. It is
then cut into pieces, one APP11 segment each, and every piece carries a
small header so a reader can put the pieces back together.

## What the specification says (read, not measured)

C2PA 2.4, §A.3.1 "Embedding manifests into JPEG", in full:

> The C2PA Manifest Store shall be embedded as the data contained in an
> APP11 marker segment as defined in JPEG XT, ISO/IEC 18477-3. Since a
> single marker segment in JPEG 1 cannot be larger than 64K bytes, it is
> likely that multiple APP11 segments will be required, and they shall be
> constructed as per the JPEG 1 standard and ISO 19566-5:2023, D.2. When
> writing multiple segments, they shall be written in sequential order, and
> they shall be contiguous (i.e., one segment immediately following the
> next).

The layout of the per-segment header is in the two ISO documents, which are
paywalled and were not read. Everything below about that layout is
**measured on this fixture**, and the acceptance criteria of SPEC-001 rest on
the measurement plus c2patool's behaviour, not on the ISO text.

## What is in the fixture (measured)

Every segment, walked with a throw-away probe script:

| offset | marker | segment | length |
|---|---|---|---|
| 0 | `FFD8` | SOI | — |
| 2 | `FFE0` | APP0 (JFIF) | 16 |
| 20 | `FFEB` | **APP11, piece 1** | 64,010 |
| 64,032 | `FFEB` | **APP11, piece 2** | 30,758 |
| 94,792 | `FFFE` | COM | 16 |
| 94,810 | `FFDB` | DQT | 67 |
| 94,879 | `FFC4` | DHT | 165 |
| 95,046 | `FFC0` | SOF0 | 17 |
| 95,065 | `FFDA` | SOS, then pixel data | — |
| 96,937 | `FFD9` | EOI | — |

The two APP11 pieces are contiguous (20 + 2 + 64,010 = 64,032) and sit
before the tables, right after APP0.

Each APP11 segment's payload begins with a 16-byte header:

| bytes | field | piece 1 | piece 2 | meaning |
|---|---|---|---|---|
| 2 | CI, common identifier | `JP` | `JP` | this APP11 carries a JUMBF box |
| 2 | En, box instance number | 529 | 529 | pieces of one box share it |
| 4 | Z, packet sequence number | 1 | 2 | order of the pieces |
| 4 | LBox | 94,740 | 94,740 | total length of the box, repeated in every piece |
| 4 | TBox | `jumb` | `jumb` | box type, repeated in every piece |
| rest | box data | 63,992 bytes | 30,740 bytes | — |

Reassembly: LBox and TBox **once**, then the data of every piece in order.
8 + 63,992 + 30,740 = **94,740 = LBox**, byte-exact. Concatenating whole
payloads instead would put `LBox`+`jumb` in twice and be 8 bytes too long.

The reassembled store: 94,740 bytes, **SHA-256
`f47af93e8afe0f71912e4c7545184ace2fb2cd5628b4a3ac832e591ac33546a3`**. Its
first bytes are `00017214 6a756d62 0000001e 6a756d64 63327061 …` — LBox,
`jumb`, then a `jumd` description box whose UUID begins with `c2pa`. Reading
that is M2. This hash is SPEC-001's oracle.

## Two things c2patool does that SPEC-001 must copy (measured)

Two variants of the fixture were built by moving whole segments, nothing
else, and given to c2patool 0.27.22:

1. **Non-contiguous**: the COM segment moved between the two APP11 pieces.
   c2patool still extracts and validates the store (`claimSignature.validated`)
   and then reports `assertion.dataHash.mismatch` — the hash binding (M4)
   notices that bytes outside the store moved. The reassembled store from
   this variant has the same SHA-256 as above. So: **extraction tolerates a
   gap between pieces**; the verdict does not, but that is M4's job.
2. **Swapped**: piece 2 placed before piece 1. c2patool stops with
   `Error: invalid embedded file box`. It does **not** sort pieces by Z; it
   reads them in file order and expects 1, 2, 3, …. Sorting would make this
   verifier more lenient than its oracle, so SPEC-001 requires Z to be
   strictly increasing in file order and treats anything else as an error.

## What this settles for SPEC-001

- Input: a JPEG stream. Walk markers from SOI to SOS; collect every APP11
  whose CI is `JP`; group by En; require Z = 1, 2, … in file order; LBox
  and TBox identical across pieces; output LBox+TBox once plus the data.
- Fail closed: a missing or out-of-order Z, an LBox/TBox that differs
  between pieces, a total that does not equal LBox, a segment that runs past
  the end of the file — each an error, never a partial store.
- No APP11: not an error; "no manifest store" is an outcome.
- Bounds: a maximum number of pieces and a maximum LBox, both errors when
  exceeded, before any memory is spent.
- Oracle: SHA-256 `f47af93e…46a3` on `fixture-signed.jpg`.
